# CLAUDE.md

Локальная транскрибация аудио на русском с разделением по говорящим. Всё считается на машине, наружу ничего не уходит.

Целевое железо — MacBook Air M4, 10 ядер, 16 ГБ, macOS 26.5. CUDA нет, есть `cpu` и `mps`.

## Команды

Виртуальное окружение живёт в `.venv/`, системный Python не используется — вызывать интерпретатор явно.

```bash
.venv/bin/uvicorn backend.app:app --port 8000     # приложение на http://localhost:8000
.venv/bin/python -m backend.pipeline --input запись.m4a   # обработка одного файла без веба
.venv/bin/python scripts/smoke_test.py            # жива ли модель, есть ли таймкоды слов и пунктуация
.venv/bin/python scripts/benchmark.py запись.m4a  # RTF по матрице модель × устройство
```

Проверка синтаксиса без запуска: `.venv/bin/python -m py_compile backend/*.py backend/pipeline/*.py` и `node --check frontend/app.js`.

Тестов нет. Проверка — прогон реального файла через `-m backend.pipeline` и глазами по результату.

## Архитектура

```
загрузка → ffmpeg (16 kHz mono) → диаризация (pyannote) ─┐
                                                          ├→ склейка по времени → .txt + .json
                                   → распознавание (GigaAM) ─┘
```

Диаризация и ASR работают **независимо** и режут аудио по-разному. Единственная общая система координат — время: каждое слово получает говорящего по своей середине (`backend/pipeline/merge.py`). Поэтому таймкоды слов критичны, без них точность привязки падает.

| Файл | Роль |
| --- | --- |
| `backend/config.py` | все настройки из `.env`, единственный источник значений |
| `backend/pipeline/asr.py` | GigaAM, ленивый синглтон + свой longform-цикл (энкодер на MPS в fp32) |
| `backend/pipeline/diarize.py` | pyannote, ленивый синглтон |
| `backend/pipeline/merge.py` | слова + говорящие → реплики, нумерация спикеров |
| `backend/pipeline/__init__.py` | оркестрация стадий и прогресс |
| `backend/worker.py` | фоновая очередь, строго последовательная |
| `backend/db.py` | SQLite, задачи переживают перезапуск |
| `frontend/` | одна страница на ванильном JS, без сборки |

Модели грузятся один раз на процесс и остаются в памяти (~2 ГБ). Задачи обрабатываются **по одной**: две копии модели неуютно в 16 ГБ, а безвентиляторный Air уходит в троттлинг быстрее, чем что-то выигрывает от параллелизма.

## Грабли, на которые уже наступили

**Не вызывать `transcribe_longform` и `model.forward` GigaAM на MPS.** На любом устройстве, кроме CPU, `GigaAM.forward` гонит энкодер под `torch.autocast(float16)`, и текст перестаёт совпадать с CPU: на записи 13.7 мин CTC дал 1 расхождение на 1870 слов («Угу» → «Уу»). Поэтому `asr.py` грузит модель на CPU, переносит на MPS только `preprocessor` и `encoder` и гоняет свой цикл в fp32, декодер остаётся на CPU. Так и RNNT, и CTC выдают текст побайтно как на CPU, в ~10 раз быстрее. Сверять — по md5 в `scripts/benchmark.py`.

Старые выводы «CTC на MPS молча портит текст» («планытвёр..ры» вместо «планы на четвёртый») и «MPS для RNNT бесполезен, 12.9× против 13.1×» на torch 2.10 не воспроизводятся: даже `transcribe_longform` на MPS даёт RNNT за 31 с против 247 с на CPU. Узкое место распознавания — энкодер (88% времени), а не последовательный декодер RNNT (~1%).

**`load_model` по умолчанию ставит `fp16_encoder=True`.** На CPU/MPS это ломает инференс, в `asr.load_model` передаётся `False`.

**Больше потоков torch не ускоряют.** По умолчанию 4 (производительные ядра M4); 8 дают −6% на энкодере на CPU, 10 — медленнее, потому что подключаются энергоэффективные ядра.

**Отката на `speaker-diarization-3.1` не существует.** Его конфиг качается и без принятых условий community-1, но `SpeakerDiarization.__init__` в pyannote.audio 4.x безусловно тянет PLDA из `community-1/plda`, а `download_from_hf_hub` пробрасывает 403 наружу. Доступ нужен именно к `community-1`, и в конфиге указана она. В 4.x у `Pipeline.from_pretrained` аргумент `token=`, а не `use_auth_token=`.

**pyannote.audio 4.x возвращает не `Annotation`.** `pipeline(...)` отдаёт датакласс `DiarizeOutput` (поля `speaker_diarization`, `exclusive_speaker_diarization`, `speaker_embeddings`) — `itertracks` у него нет, старый код падает с AttributeError. `Annotation` приходит только при `legacy=True`. Оба варианта разбираются в `diarize._extract_annotation`, и по умолчанию берётся эксклюзивная разметка: в ней нет перекрывающейся речи, и слово не попадает сразу в двух говорящих.

**pyannote.audio 4.x по умолчанию шлёт телеметрию наружу** — длительность записи и запрошенное число говорящих уходят на `otel.pyannote.ai` (`telemetry/config.yaml`, `metrics_enabled: true`). Для инструмента, который «наружу ничего не отправляет», это неприемлемо. Гасится `PYANNOTE_METRICS_ENABLED=false`, выставляется в `config.py` до импорта pyannote.

**Один говорящий в результате ничего не значит сам по себе.** Отличать по `meta`: `diarization_enabled=false` — стадия пропущена; `true` при `diarization_turns=0` — pyannote не нашёл речи; `true` при `diarization_turns>0` — действительно услышал одного. Логи `diarize.py` пишут число интервалов и говорящих на каждом прогоне; раньше их не было, и разбор упирался в гадание.

**`HF_TOKEN` нужен дважды** — для VAD внутри GigaAM (`pyannote/segmentation-3.0`) и для диаризации. Условия надо принимать на обеих страницах.

**`.transcribe()` работает только до 25 секунд.** Для всего остального — `transcribe_longform`.

**Реплики режутся по границам VAD-сегментов,** а не только по паузам между словами. Без этого монолог превращается в один абзац на несколько минут: пауз длиннее `UTTERANCE_GAP` в связной речи почти не бывает.

**Статика отдаётся с `Cache-Control: no-cache`** (`NoCacheStatic` в `app.py`). Иначе правка `frontend/app.js` не видна до ручной очистки кэша.

**Спикеры нумеруются по порядку первого появления в записи,** а не по ID из pyannote — иначе «Спикер 2» заговорит первым.

**Исходник загрузки удаляется после успешной обработки** (`worker._process`): плеер играет wav из `data/wav`, а исходник — часто видео на сотни мегабайт. У упавших задач исходник остаётся. Если wav пропал, `/api/jobs/{id}/audio` отдаёт исходник; MIME берётся из `SOURCE_MEDIA_TYPES`, потому что `mimetypes` на macOS отдаёт для .m4a `audio/mp4a-latm`, которое Safari не играет.

**`wav_path` пишется в базу при старте обработки, а не по успеху.** Иначе wav упавшей или прерванной задачи становится сиротой, и удаление задачи его не находит.

**На macOS нет `timeout`.** Не использовать в командах.

## Скорость

Замеры на M4, встреча 13.7 мин (822 с), два говорящих. Результат на mps побайтно совпадает с cpu — и разметка говорящих, и текст с таймкодами слов.

| Стадия | cpu | mps (дефолт) |
| --- | --- | --- |
| диаризация | 512 с | 75 с |
| распознавание `v3_e2e_rnnt` | 247 с (VAD 28 + энкодер 216) | 25 с (VAD 4 + энкодер 18) |
| распознавание `v3_e2e_ctc` | 239 с | 22 с |
| весь пайплайн | 831 с, RTF 1.0× | 101 с, RTF 8.1× (с холодным стартом) |

Диаризация остаётся самой долгой стадией — около трёх четвертей времени. Без неё запись 5 мин распознаётся за 6 с. Час аудио с диаризацией — по пропорции около 7–8 минут (на длинных записях не замерялось, Air может троттлить).

Параллельный запуск распознавания и диаризации внутри задачи не замерялся: обе стадии теперь на GPU и делили бы его.

Только версии `v3_e2e_*` дают пунктуацию и нормализацию («123 млн ₽», «18%»). Обычные `v3_ctc`/`v3_rnnt` выдают сплошной текст строчными.

## Соглашения

- Интерфейс, сообщения об ошибках и комментарии в коде — на русском.
- Ошибки должны быть действием, а не трейсбеком: называть, что именно сделать. Внутренние пути в сообщения не просачиваются (`audio._clean`).
- Фронтенд без сборки и без зависимостей. Кликабельные элементы — настоящие `<button>`, чтобы работала клавиатура.
- Прогресс тянется поллингом раз в секунду, без WebSocket.
- `data/` и `.env` в `.gitignore`. Токен в репозиторий не попадает.

## Состояние

Работает и проверено вживую: загрузка → очередь → прогресс → результат, скачивание `.txt`/`.json`, переименование спикеров, обработка битого файла и записи без речи.

Разделение по говорящим выбирается для каждой загрузки радиокнопкой в интерфейсе (поле формы `diarize`, колонка `jobs.diarize`, в CLI `--diarization/--no-diarization`). `DIARIZATION_ENABLED` из `.env` — только значение по умолчанию: и для переключателя, пока пользователь ничего не выбрал (выбор запоминается в `localStorage`), и для старых задач с `diarize = NULL`.

Время обработки замеряется: по стадиям в `meta.stage_seconds`, целиком по задаче в колонке `processing_seconds`, RTF в `meta.realtime_factor` (та же семантика «×быстрее реального времени», что и в `scripts/benchmark.py`). `meta.cold_start` отмечает прогон, оплативший загрузку моделей, — иначе его низкий RTF выглядит выбросом.

**Путь с диаризацией проверен на живой речи.** Запись встречи 13.7 мин, два собеседника: pyannote нашёл 214 интервалов и ровно двух говорящих, роли (кто спрашивает, кто объясняет) держатся до конца записи. Загружается `community-1`, `legacy=False`, кластеризация VBx, разметка берётся эксклюзивная.

Что диаризация не ловит: короткие поддакивания («угу», «да») на фоне чужой речи и перебивки в середине чужой реплики иногда достаются не тому спикеру. Это предел привязки по середине слова, а не сбой — 22% реплик здесь длиной в 1–2 слова.

Если спикеры слипаются — в `.env` есть `MIN_SPEAKERS` / `MAX_SPEAKERS` / `NUM_SPEAKERS`, они прокидываются в pyannote (и флагами `--min-speakers` / `--max-speakers` в CLI). Эффективные значения видны в `/api/health`.

Проверка диаризации делалась на синтетическом диалоге (`say` + питч-сдвиг для второго голоса). Это проверяет работоспособность связки, но не качество на живой речи — нужен прогон на реальной записи встречи.
